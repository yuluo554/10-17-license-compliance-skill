## 零、贯穿全部模块的判定纪律

| 编号 | 纪律 | 落点 |
| --- | --- | --- |

## M1 清单解析与 SPDX 归一化

### 1.1 输入识别

按**文件名形态**识别，不按目录：

| 文件名 | 解析器 | 关键字段 |
| --- | --- | --- |
| `package.json` | `parse_package_json` | `dependencies` / `devDependencies` / `peerDependencies` / `optionalDependencies`，`license` / `licenses` |
| `package-lock.json` | `parse_package_lock` | v2/v3 的 `packages` 映射（键 `""` 为根包，跳过）；v1 的 `dependencies` 树 |
| `requirements.txt` | `parse_requirements` | 每行 `name[extras]==version`；注释、`-r`、`-e`、VCS 行显式忽略并计注记 |
| `pyproject.toml` | `parse_pyproject` | `[project].dependencies`、`[project].optional-dependencies`、`[tool.poetry.dependencies]` |
| `go.mod` | `parse_go_mod` | `require` 块与单行 `require` |
| `pom.xml` | `parse_pom` | `<dependencies><dependency>`，`<licenses><license>` |

未知文件名 → 不是清单，`UsageError`（exit 2）并列出支持的文件名。**不猜**。

#### 依赖许可证的来源（M1 落地补充，决策 D19）

清单文件多数**不含依赖各自的许可证**（`requirements.txt` / `go.mod` 只有名字与版本）。
本解析器只接受**显式写出来的**许可证值，**绝不**按包名或生态惯例推断。支持的注记形态：

| 文件 | 显式注记形态 |
| --- | --- |
| `package.json` | 依赖值可为对象 `{"version": "1.0.0", "license": "MIT"}`；也接受 `licenses` 数组、`classifiers` |
| `package-lock.json` | v2/v3 的 `packages[*].license`（原生字段）；v1 的 `dependencies[*].license` |
| `requirements.txt` | 行尾注记 `example-pkg-a==1.0.0  # license: MIT` |
| `pyproject.toml` | `dependencies` 元素可为内联表 `{name="x", version="1", license="MIT"}` |
| `go.mod` | 行尾注记 `// license: MIT` |
| `pom.xml` | `<dependency>` 内可含 `<license>MIT</license>` |

没有注记 → `raw_license = None` → 第 4 级 `truncated_fallback` + 待人工确认。
根包/项目的 `license`、`<licenses>`、项目级 `classifiers` **不传递给依赖**，
只在 `parse_notes` 里记一条 `root_license_ignored`。

### 1.2 记录结构

```json
{
  "package": "example-pkg-a",
  "version": "1.2.3",
  "raw_license": "MIT",
  "spdx_id": "MIT",
  "confidence": "license_expression",
  "evidence": {
    "file": "package.json",
    "locator": "dependencies.example-pkg-a / license",
    "line": 12,
    "ruleset_version": "r0.1.0",
    "details_url": "https://spdx.org/licenses/MIT.json"
  }
}
```

- `evidence.locator` 一律「字段路径」形态；`line` 是源文件行号（可复算），无法给出时 `null`。
- 顶层另有 `format` / `format_version` / `source_files` / `parse_notes`（每条注记 `code` + `message` + `file` + `line`）。

### 1.3 四级可信度链（命中即停，不跨级合并）

1. **`license_expression`**：结构化表达式字段。
   - `package.json`：`license` 为字符串 / `{type, url}`；`licenses` 为数组时合并为 `AND`。
   - `pyproject.toml`：PEP 621 `license = {text = "MIT"}` 或 `license = "MIT"`；Poetry `license = "MIT"`。
   - `pom.xml`：`<licenses><license><name>` 或 `<url>`。
   - 结果必须能被 SPDX 表达式解析器接受（见 1.4），否则**降级到下一级**并记注记。
2. **`trove_classifier`**：仅 Python 生态（`pyproject.toml` 的 `classifiers`、`setup.cfg` 若支持）。
   - 只认 `License :: OSI Approved :: <name>` 与 `License :: <name>` 形态；经 `trove-map.json` 精确映射。
   - 映射表未命中 → 降级，**不模糊匹配**。
3. **`license_first_line`**：取 `raw_license` 的**第一行**（`\r\n`/`\n`/`\r` 切分后 `strip()`）。
   - 仅允许**锚定模式**：整行等于 `SPDX id`、或以 `SPDX id + " License"` / `SPDX id + " OR "` 等受限形态开头。
   - 禁止在整段文本里搜关键词；**首行超过 200 字符直接不匹配**（防止把全文当首行）。
4. **`truncated_fallback`**：以上都不成 → `spdx_id = null`，`raw_license` 截断到 200 字符（保留首行），标 `待人工确认`。

`confidence` 枚举固定四级，不得新增第五级。

### 1.4 SPDX 表达式解析

文法（充分子集）：

```
expr    := term (OR term)*
term    := factor (AND factor)*
factor  := id ['+' | '-'?] | id 'WITH' exception | '(' expr ')'
```

- 词法：`AND` / `OR` / `WITH` 大小写**必须**大写（SPDX 规范）；小写视为普通 token → 解析失败 → 降级。
- 标识符必须命中 `references/spdx/licenses.json` 的 `licenseId` 集合（含 `-only` / `-or-later`）。
- `WITH` 后的例外必须命中 `exceptions.json` 的 `licenseExceptionId`；未命中 → 该分支 `unknown-exception` + 待确认，**但表达式不整体丢弃**。
- **不做版本归一化**：`GPL-2.0-only` 原样保留；`GPL-2.0`（旧式写法）按 SPDX 3.29 是否存在决定：存在则原样，不存在则以 `deprecated` 标记 + 待确认。
- `GPL` / `Apache` / `BSD` 这类族名 → `<族>-unknown` + 待确认，**不取最新版**。
- 输出的 `spdx_id` 是**规范化字符串**（保留括号与运算符，运算符两侧单空格）；`OR` 与 `AND` 不展开、不重排（`OR` 求值在 M4 做）。

### 1.5 拒绝条件

- 文件不是 UTF-8（含 BOM 处理：BOM 去掉后按 UTF-8 解码）→ `UsageError`。
- `package-lock.json` 版本既非 v1/v2/v3 → `UsageError`，列出检测到的 `lockfileVersion`。
- TOML 超出受限子集 → 该文件 `parse_notes` 记 `toml_unsupported`，**不产依赖**且 exit 2（输入不可用）。
- 空文件 / 只有空白 → `UsageError`。

### 1.6 输出与门禁

- 落 `inventory.json`（`--out-dir`）。
- 每条记录必须挂 `evidence.ruleset_version` 与 `details_url`；缺任一 → 该条不进 `dependencies`，进 `pending_confirmation`。
- 解析器是纯函数：同输入同输出；双跑逐字节一致（测试锁）。

> **M1 落地补充（决策 D22）**：`dependencies` 与 `pending_confirmation` **不是互斥列表**。
> 一条记录可以有完整证据（进 `dependencies`）同时带 flag（也进 `pending_confirmation`）。
> `spdx_id = null` 或 `<族>-unknown` 的记录没有可指向的 SPDX 原文，因此**不伪造 `details_url`**，
> 只出现在 `pending_confirmation` 里，并在 `missing` 中写明缺什么。

## M2 许可证画像与义务矩阵

### 2.1 输入

`inventory.json` + `references/ruleset/*` + `references/spdx/licenses.json`。

### 2.2 输出 `profile.json`

每个**不同** SPDX 原子 ID 一条（表达式先拆成原子）：

```json
{
  "spdx_id": "GPL-2.0-only",
  "tier": "strong-copyleft",
  "obligations": ["retain-copyright", "include-license-text", "mark-modifications", "provide-source", "same-license"],
  "is_osi_approved": true,
  "is_fsf_libre": true,
  "patent_clause": {"present": false, "anchor": null, "checked_on": "2026-10-17"},
  "trademark_clause": {"present": false, "anchor": null, "checked_on": "2026-10-17"},
  "evidence": {"rule_id": "...", "license_text_anchor": "§...", "checked_on": "2026-10-17", "details_url": "..."}
}
```

### 2.3 规则包结构

`references/ruleset/tiers.json`：

```json
{
  "schema_version": 1,
  "ruleset_version": "r0.1.0",
  "entries": [
    {
      "license_id": "GPL-2.0-only",
      "tier": "strong-copyleft",
      "obligations": ["retain-copyright", "include-license-text", "mark-modifications", "provide-source", "same-license"],
      "patent_clause": {"present": false, "anchor": null},
      "trademark_clause": {"present": false, "anchor": null},
      "anchor": {"source": "spdx-license-text", "ref": "GPL-2.0-only.json#licenseText", "section": "§5"},
      "verified": true,
      "checked_on": "2026-10-17"
    }
  ]
}
```

- `tier` 五档枚举：`permissive` / `weak-copyleft` / `strong-copyleft` / `network-copyleft` / `source-available`。
- `obligations` 枚举固定，规则包只能取下列值；引擎不新增：
  `retain-copyright` / `include-license-text` / `mark-modifications` / `provide-source` / `network-source` / `patent-grant` / `trademark-restriction` / `same-license`。
- OSI / FSF 状态**只从 SPDX 快照取**，不写进 ruleset（避免两份真相）。
- 每条 `verified=false` 或 `anchor` 不可解析 → loader 拒绝该条，进 `disabled`，**不参与任何判定**。
- 覆盖范围：首期只承诺**清单里实际出现的 SPDX ID**；规则包生成器对未覆盖 ID 记 `uncovered`，画像输出 `tier: null` + 待确认，**不猜档位**。

### 2.4 判定纪律

- 五档与义务项定义只在 `tiers.json`（及 `obligations.json` 的说明表）出现一次；`plan/01` 与报告只引用名称。
- `AND` / `OR` 表达式的画像在 M4 求值；M2 只给原子画像。
- FSF Libre 仅辅助展示，**不参与任何判定**（测试断言判定函数不读该字段）。

### 2.5 M2 落地补充（2026-10-17，决策 D23–D26）

实现落点：`src/licaudit/assess/profile.py`；CLI 为 `assess --profile-only`。

- **原子拆分**：复用 `spdx_expr.parse_expression` 的 `atoms`，不另写一套文法。
  `GPL-2.0-only WITH Classpath-exception-2.0` 只拆出 `GPL-2.0-only`（例外不是许可证）。
  表达式解析失败**不丢记录**：整串作为单个原子保留，并写 `notes[].code = expression_unparsed`。
- **输入面**：`dependencies` 与 `pending_confirmation` 两个列表的 `spdx_id` 都进原子集合
  （D22：两列表不互斥；只在 pending 里的记录同样需要画像）。引擎同时接受
  `pending_confirmation[].record` 的外层包装与裸记录两种形状。
- **义务顺序**：规则表按可读顺序书写，产物一律按 `contract.OBLIGATIONS` 的固定顺序输出，
  保证下游报告/CSV 不因规则表书写顺序而漂移。
- **条款三态**：有规则且 `present=false` → `false`（该许可证确实没有此条款）；
  无规则 → `present = null` + `anchor = null` + `checked_on = null`（不知道）。
  把「不知道」写成 `false` 是实质性误判，测试锁死（K32）。
- **未覆盖原因码**（`pending_confirmation[].reasons`，字典序）：
  `tier_uncovered`（基码，永远在）/ `rule_disabled` / `rule_duplicated` / `unknown_family`。
  `<族>-unknown` 走这条路径；`Proprietary Internal Use Only` 这类族外串也走这条路径。
- **disabled 两道门**：loader 第一道（K10），引擎 `_is_disabled_entry` 第二道。
  第二道不是冗余：调用方可能不经过 loader 直接构造规则包对象；测试用 fake ruleset 锁死。
- **`disabled_rules`** 是 loader 拒绝条目的投影（`file` / `index` / `id` / `reasons`），
  每条被拒都要可见，不允许静默消失。
- **`notes`** 目前只有 `expression_unparsed` 一种码；新增码必须同步本节与测试。
- **真值**：`data/truth/profile.json`（`format = licaudit-profile-truth`）由
  `tools/gen_profile_truth.py` 从 curated 规则表**直接推导**，生成器不 import 生产画像引擎；
  锚点可定位性用文件内的朴素实现独立校验。真值同时覆盖「有档位」与「`tier: null`」两侧。
- **基准**：`bench --only m2` 走 `verify.verify_profile`，逐条比对
  `tier` / `obligations` / OSI / FSF / 两项条款 / `pending.reasons`，并额外断言
  「有档位 → 必须有可定位锚点与 `checked_on`」。`bench`（无 `--only`）现在跑 m1 + m2。

## M3 使用场景判定

### 3.1 输入与八场景定义

题面的**八种场景**是唯一对外枚举，内部由 `(delivery, link_mode)` 两轴表达。两者一一映射，**映射表写在代码常量里并由测试锁死**：

| 场景 ID（对外） | 中文 | `delivery` | `link_mode` | 网络交互询问 |
| --- | --- | --- | --- | --- |
| `internal` | 内部使用 | `internal` | `none` | 否 |
| `distribute-binary` | 分发二进制 | `binary` | `none` | 否 |
| `distribute-source` | 分发源码 | `source` | `none` | 否 |
| `saas` | SaaS | `saas` | `none` | **是** |
| `static-link` | 静态链接 | 由用户同时给定 | `static` | 否 |
| `dynamic-link` | 动态链接 | 由用户同时给定 | `dynamic` | 否 |
| `separate-process` | 独立进程 | 由用户同时给定 | `separate-process` | 否 |
| `container-image` | 容器镜像 | `container` | `none` | 可选 |

说明：静态/动态链接与独立进程是**链接方式**轴，必须与「交付形态」组合使用（如「分发二进制 + 静态链接」）；`internal`/`saas`/`container` 三类默认 `link_mode=none`，但允许用户额外声明链接方式以细化判定。`--scenario` 直接接受上表八个 ID；`--delivery` + `--linking` 是等价写法，两者同时给出且矛盾 → `UsageError`（exit 2）。

```json
{
  "scenario": "saas",
  "delivery": "saas",
  "link_mode": "none",
  "network_interaction": true,
  "answered_by": "user",
  "raw_answer": "我们通过 Web 提供服务，用户可远程访问"
}
```

- 命令行形态：`--scenario saas --network-interaction yes --scenario-note "..."`。
- **必须落盘用户原始回答**（`raw_answer` + `answered_by`）；不得由模型代填。
- 场景未给出 → `UsageError`（exit 2），**不默认 internal**。

### 3.2 触发表（规则包）

`references/ruleset/scenario-triggers.json`：

```json
{
  "schema_version": 1,
  "entries": [
    {
      "id": "T-DIST-001",
      "tier": "strong-copyleft",
      "scenarios": ["distribute-binary", "distribute-source", "container-image"],
      "link_modes": ["static", "dynamic", "separate-process", "none"],
      "trigger": "distribution",
      "obligations": ["provide-source", "same-license"],
      "anchor": {"source": "license-text", "ref": "GPL-3.0-only.json#licenseText", "section": "§5"},
      "verified": true,
      "checked_on": "2026-10-17"
    },
    {
      "id": "T-NET-001",
      "tier": "network-copyleft",
      "scenarios": ["saas"],
      "link_modes": ["static", "dynamic", "separate-process", "none"],
      "network_interaction": true,
      "trigger": "network-interaction",
      "obligations": ["network-source"],
      "anchor": {"source": "agpl-3.0", "ref": "§13"},
      "verified": true,
      "checked_on": "2026-10-17"
    },
    {
      "id": "T-STATIC-001",
      "tier": "weak-copyleft",
      "scenarios": ["distribute-binary", "distribute-source"],
      "link_modes": ["static"],
      "trigger": "static-link",
      "obligations": ["provide-source", "mark-modifications"],
      "anchor": {"source": "license-text", "ref": "LGPL-2.1-only.json#licenseText", "section": "§6"},
      "verified": true,
      "checked_on": "2026-10-17"
    }
  ]
}
```

判定算法（固定顺序）：

1. 取依赖的 `tier`；无画像 → `pending`。
2. 逐条匹配 `tier` + `scenarios`（包含用户场景）+ `link_modes`（包含用户链接方式）+ `network_interaction`（若条目声明则必须与用户回答一致）；全部条件满足即触发。
3. 结果 = 触发集合的并集，并记录命中的 `rule_id`（可多条）。
4. 未命中任何条目 → `not_triggered`（这是「该场景不触发」，不是 `not_applicable`）。
5. 用户未回答 / 回答矛盾 / 场景与链接方式组合非法 → `pending_confirmation`。

**硬语义**：

- 「商用」**不是**输入项，也不得作为触发条件；测试断言 `scenario.json` 的输入字段集合不含 `commercial`。
- AGPL §13 是**独立触发点**：`saas` + `network_interaction=true` 即使 `delivery != binary` 也触发；相反 `internal` + 无网络交互 → 不触发。
- `container-image` 按交付物处理：镜像被分发 → 视同 `distribute-binary`；只在内网运行 → 视同 `internal`。**该映射由用户在场景选择时决定**，引擎不做推断。
- 链接方式只在 `tier ∈ {weak-copyleft, strong-copyleft, network-copyleft}` 时影响判定；宽松档不因链接方式触发义务（由触发表不写宽松条目来承担，引擎不写 if）。

### 3.3 输出 `scenario.json`

每条 `(package, scenario)`：

```json
{
  "package": "example-pkg-a",
  "scenario": "saas",
  "link_mode": "none",
  "triggers": ["network-interaction"],
  "verdict": "triggered",
  "evidence": {"rule_ids": ["T-NET-001"], "user_answer": "...", "answered_by": "user"}
}
```

`verdict` 三态：`triggered` / `not_triggered` / `pending_confirmation`。

### 3.4 M3 落地补充（2026-10-17，决策 D27）

实现落点：`src/licaudit/assess/scenario.py`；CLI 为 `assess --scenario ... --outbound-license ...`。

- **匹配维是交付形态场景**：触发表的 `scenarios` 列写交付形态场景（`distribute-binary` 等）；
  链接方式轴场景（`static-link` / `dynamic-link` / `separate-process`）必须同时给出交付形态，
  引擎把它们归一到交付形态场景 + `link_mode` 后再匹配。`--scenario` 与
  `--delivery` + `--linking` 是等价写法；两者同时给出且矛盾 → `UsageError`（exit 2）。
- **触发表条目结构**（`scenario-triggers.json`）：`id` / `tier` / `scenarios` / `link_modes` /
  （可选）`network_interaction` / `trigger` / `obligations` / `anchor` / `verified` / `checked_on`；
  生成器与 tiers 同口径验证锚点 quote 可在 SPDX 全文逐字定位（D20），非法即 `verified=false`。
- **container-image 视同交付物**：体现在触发表里，`container-image` 与 `distribute-binary` / `distribute-source`
  同列分发条目——镜像被分发即分发；只在内网运行应选 `internal`。该映射由用户在场景选择时决定，引擎不做推断。
- **只有 6 条规则**：strong/network 分发、AGPL §13 网络交互、weak 分发、weak 静态链接、
  source-available 托管服务限制。宽松档不写条目 → 永不触发（引擎不写档位特判，K4）。
- **AGPL §13 独立触发点**（K13）：条目声明 `network_interaction: true`，只要用户回答「是」，
  任何交付形态（含 `internal`）都参与匹配；回答「否」则不匹配。
- **三态来源**：
  - `triggered` / `not_triggered` 由查表得出；
  - `pending_confirmation` 来自：未覆盖档位（`tier_unavailable`）、`spdx_id` 缺失、
    表达式求值不出（`expression_unresolved`；**M4 起**改为：求值成功即按所选原子下结论，
    只有「有原子未覆盖档位 / 表达式无法解析」才待确认 —— 见 §4.7 与决策 D32）、
    链接方式轴场景缺交付形态（`delivery_unanswered`）、
    saas 未回答网络交互（`network_interaction_unanswered`）、
    saas 回答「无网络交互」（`network_interaction_contradicts_scenario`，矛盾）、
    container-image 网络交互未回答且该档位存在网络候选条目（不取宽松默认）。
- **不猜档位**（K31）：`tier` 为 `null` 的条目直接 `pending_confirmation`，不进触发查表。
- **用户回答落盘**：顶层 `scenario` / `delivery` / `link_mode` / `delivery_scenario` /
  `network_interaction` / `answered_by` / `raw_answer` / `outbound_license`；
  引擎不代填，`raw_answer` 为空时只落一条 `raw_answer_missing` 注记。
- **outbound 校验**：M3 只是把 M4 的输入收进来并拒非法值（`pending` 或快照内的 SPDX 表达式；
  未知 ID → exit 2），不做兼容性判定。
- **退出码**：全量模式「有待确认项 → 1，否则 0」；触发本身不改退出码（阻断分级属 M5）。
- **真值**：`data/truth/scenario.json`（`format = licaudit-scenario-truth`）由
  `tools/gen_scenario_truth.py` 从 curated 触发表**直接推导**，生成器不 import 生产场景引擎；
  判定表 230 行 + 1 条 `tier: null` 待确认。`bench --only m3` 走 `verify.verify_scenario` 逐行对账。

## M4 冲突与兼容性分析

### 4.1 输入

`inventory.json` + `profile.json` + `scenario.json` + `--outbound-license <SPDX 表达式>`（必填）。

- 未给 `--outbound-license` → `UsageError`（exit 2），除非 `--outbound-license pending` 显式表示「尚未决定」。
- `pending` → 依赖-项目冲突全部输出 `pending`，**不猜**。

### 4.2 输出 `conflicts.json`

两类：

1. **依赖间冲突**：两条依赖的许可证不可同时满足。
2. **依赖 × outbound 冲突**：依赖义务与项目准备采用的分发许可不相容。

```json
{
  "pair_id": "CP-GPL2-APACHE2",
  "left": "GPL-2.0-only",
  "right": "Apache-2.0",
  "basis": "Apache-2.0 §4 附加专利/赔偿条款构成 GPLv2 不允许的额外限制",
  "resolution": "incompatible",
  "evidence": {"source": "curated", "anchor": "Apache-2.0.json#licenseText §4", "checked_on": "2026-10-17", "cross_check": "OSADL mirror (advisory)"}
}
```

### 4.3 规则包 `conflict-pairs.json`

```json
{
  "schema_version": 1,
  "entries": [
    {
      "pair_id": "CP-GPL2-APACHE2",
      "left": "GPL-2.0-only",
      "right": "Apache-2.0",
      "resolution": "incompatible",
      "basis": "...",
      "anchor": {"source": "license-text", "ref": "Apache-2.0.json#licenseText", "section": "§4"},
      "cross_check": {"source": "osadl-mirror", "status": "advisory", "checked_on": "2026-10-17"},
      "verified": true,
      "checked_on": "2026-10-17"
    }
  ]
}
```

- 冲突对是**无向**的：匹配时 `(left,right)` 与 `(right,left)` 等价（测试锁）。
- `verified=false` 或锚点不可解析 → 不加载。
- OSADL 只作 `cross_check`，**不参与判定**；`advisory` 字段可缺省。

### 4.4 表达式求值

- 单个依赖的 `spdx_id` 若是表达式：
  - `OR` → **取最宽松**的原子（档位序 `permissive < weak-copyleft < strong-copyleft < network-copyleft < source-available`）。
  - `AND` → **取最严格**的原子。
  - `WITH` → 保留例外标签参与匹配；例外本身不改变档位（除非规则包显式给 `exception_tier_overrides`）。
- 求值结果写进 `conflicts.json` 的 `expression_evaluations`，带所选原子与理由，**不得只给最终 ID**。

### 4.5 项目 outbound 判定

- `outbound` 已知：把每个依赖的档位/义务与 outbound 的档位比较：
  - 依赖强于 outbound（如 GPL 依赖 + MIT outbound 且已分发）→ `incompatible`。
  - 依赖与 outbound 相同档位或更宽松 → `compatible`。
  - 义务项冲突（如 `same-license` vs 项目要求 `Apache-2.0-only`）→ `incompatible`，带义务项依据。
- `outbound = pending` → 所有条目 `pending`，输出文案固定「项目自身许可证待定」，**不按最宽松默认**。
- `outbound` 本身是未知 ID → exit 2。

### 4.6 传染范围聚合

- 按 M3 的链接/分发边界向上聚合：静态链接 → 同一作品；动态链接 → 衍生作品边界按规则包 `linkage-boundary.json`（M4 定稿）；独立进程 → 不聚合；AGPL 网络服务 → 聚合到服务边界。
- 聚合结果落 `scope_aggregation`，每条带 `basis_rule_id`。

### 4.7 M4 落地补充（2026-10-17，决策 D32–D34）

**产物 `conflicts.json` 顶层字段**（`conflict.CONFLICT_TOP_LEVEL_FIELDS`）：

`format` / `format_version` / `ruleset_version` / `scenario` / `delivery` / `link_mode` /
`outbound_license` / `outbound_tier` / `dependency_conflicts` / `outbound_conflicts` /
`expression_evaluations` / `uncovered_pairs` / `pending_confirmation` / `notes`

- 两类冲突条目（依赖间、依赖 × outbound）**共用** `contract.CONFLICT_FIELDS` 记录形态。

- 顶层 `pending_confirmation` 是 `resolution = pending` 条目的投影，带原因码

  `spdx_id_missing` / `expression_unresolved` / `curated_pair_pending`）。

**依赖间冲突**（`dependency_conflicts`）：

- 按**无向键**（`left`/`right` 排序后的二元组）查 `conflict-pairs.json`；产物里按规则表书写顺序输出。
- 按「起支配作用的许可证」归并依赖：同一许可证的多条依赖合成一条，包名登记在
  `evidence.packages`（无向，两侧各一份）。原始 `spdx_id` 一并留在 `evidence.node_raw_spdx_ids`。
- 规则表未登记的组合**不产出条目**，只计 `uncovered_pairs`（`count` / `items` / `items_truncated`；
  上限 `UNCOVERED_PAIR_LIMIT = 100`）。**该计数不改退出码**：未知**单个**许可证已经由画像
  `tier: null` → 依赖 × outbound 待定 → exit 1 拦住，未登记组合只是规则包覆盖度事实。
- 规则表侧三道门（`tools/gen_ruleset.build_conflict_pairs`）：`left`/`right` 必须在 SPDX 快照内且不相同、
  无向组合不得重复登记、锚点 `quote` 必须能在原文逐字定位（D20 同口径）；不通过 → 该条不产出或
  `verified=false`（loader 拒进 `disabled`）。

**表达式求值**（K16）：递归按文法求值 —— `OR` 取最宽松、`AND` 取最严格（`contract.TIER_RANK`），
同档位并列取**出现顺序在前**的原子（确定性）；`WITH` 例外标签保留在记录里但不改变档位
（规则包目前没有 `exception_tier_overrides` 数据，也就没有例外改档位的通路）。
任一支缺少档位 → `resolved = false`（不猜）。记录写进 `expression_evaluations`，字段：
`source`（`dependency` / `outbound`）/ `package` / `expression` / `operator` / `atoms` /
`selected` / `tier` / `resolved` / `reason` / `exceptions`。
**单原子记录不进该列表**（无组合可求值）；outbound 的求值记录**始终保留**，用于说明 `outbound_tier` 的来源。

**依赖 × outbound**（`outbound_conflicts`，每个不同的依赖许可证一条）：

| 情形 | 结论 | 依据文案 |
| --- | --- | --- |
| `outbound = pending` | `pending` | 固定「项目自身许可证待定」 |
| 依赖 `spdx_id` 缺失 / 表达式求值不出许可证 | `pending` | 「依赖的许可证未识别…」 |
| 依赖档位未覆盖（`tier: null`） | `pending` | 「依赖档位未覆盖…」 |
| outbound 表达式求值不出档位 | `pending` | 「项目 outbound 表达式无法求值…」 |
| 依赖档位强于 outbound 档位 | `incompatible` | 「依赖档位 X 强于项目 outbound 档位 Y…」 |
| 依赖要求 `same-license` 且 outbound 选的是**另一个**许可证，且 outbound 档位**不高于**依赖档位 | `incompatible` | 「依赖要求同许可发布…」 |
| 其余 | `compatible` | 「…未发现档位级冲突」 |

- 最后一条判据的档位护栏是**刻意**的：GPLv3 作品合并进 AGPLv3 由 AGPL §13 明文允许，
  「依赖被更严格档位吸收」不算冲突（决策 D33）。反过来 GPL-3.0-only 依赖 + GPL-2.0-only outbound
  （同档位、不同许可证）仍是 `incompatible`。
- outbound 用到的许可证**不在依赖里**时，档位由同一份规则包（`profile.profile_ids`）现算，
  不得因为「画像里没有」就待定。
- outbound 的合法性（未知 ID → exit 2）仍由 `scenario.validate_outbound` 在编排层挡住，M4 不重复实现。

**退出码**：全量模式任一 `pending` 或 `incompatible` → 1（`conflict.has_blocking_finding`），

**§4.6 传染范围聚合本轮未实现**（决策 D34）：`linkage-boundary.json` 尚未定义，判定只做档位级比较；

读成「按链接/分发边界聚合后」的结论。档位级比较是**粗判**：`MPL-2.0` 依赖 + `MIT` outbound 会被判

**D32：表达式求值回填 scenario 判定**。M3 曾对「原子结论不一致」的表达式输出

`conflict.evaluate_expression`（同一份实现，测试断言两模块引用同一函数）：

- 求值成功且**没有任何原子**本身待确认 → 按选中原子的结论（`OR` 选最宽松 ⇒ `MIT OR GPL-3.0-only`
  在分发场景下是 `not_triggered`）；`evidence.expression_evaluation` 留下选择过程。

- 求值失败（有原子未覆盖档位、表达式无法解析）→ 待确认 + `expression_unresolved`。

## M5 处置建议与清单输出

### 5.1 处置分级（唯一枚举）

| 级别 | 语义 | 触发条件（规则包） |
| --- | --- | --- |
| `ok` | 可直接用 | 未触发任何需要行动的义务 |
| `declare` | 需补声明 | 仅触发 `retain-copyright` / `include-license-text` 类义务 |
| `isolate` | 需隔离（进程分离 · 容器边界） | 触发 `provide-source` 但可通过边界隔离规避，或 `network-source` 可通过隔离规避 |
| `replace_or_license` | 需替换或取得商业授权 | `same-license` 且 outbound 不相容；或冲突对判定 incompatible 且无法隔离 |

### 5.2 五锚点门

每条处置必须同时具备：

1. `package`
2. `version`（未知时 `*`，且该条自动降级为待确认）
3. `declaration_location`（文件 + 字段/行号）
4. `spdx_id`（`null` 则降级）
5. `basis_clause`（规则包锚点：许可证文本节号或触发表 `rule_id` + 条款）

缺任一 → 该条**不进处置建议**，进「待人工确认项」并写明缺哪一项。

### 5.3 报告章节（顺序固定）

1. 概述
2. 口径声明
3. 证据锚点
4. 逐包明细
5. 风险分级
6. 处置建议
7. 待人工确认项
8. 免责声明

- 免责声明原样输出：

- `report/` 不得 import `licaudit.inventory` / `licaudit.assess`。

- 有 `pending_confirmation` 条目但无阻断级 → exit 1（待确认项要被 CI 看见，不静默通过）。

### 5.6 M5 落地补充（2026-10-17，决策 D35–D36）

实现落点：判定侧 `src/licaudit/assess/action.py`；渲染侧 `src/licaudit/report/{sections,markdown,csv_render}.py`。

**产物 `actions.json` 顶层字段**（`action.ACTIONS_TOP_LEVEL_FIELDS`）：

**决策表语义：事实 + 谓词 + 顺序**（K18）

1. 每包先算出四个**只读上游产物**的事实：
   `axes`（由场景层触发的义务项经规则表 `obligation_axes` 映射成义务轴）、

2. `when` 支持六种谓词：`axes_any` / `axes_only` / `conflict` / `pair_conflict` / `link_mode` / `verdict`；

3. 决策表**按书写顺序解释，先命中者生效**（顺序即优先级，因此生成器不排序）；
   都不命中 → `level: null` + `action_rule_uncovered`（不猜）。
4. 生成器两道结构门（与手写表同源、独立实现）：**覆盖完备**（由 curated 场景触发表推出的可达义务轴
   集合 × 确定冲突结论 × 依赖间冲突 × 链接方式 × 场景结论 = 192 组输入，每组都必须有结论）+
   **无死规则**。表补不完 → `--check` 红，不把口径漏洞伪装成谨慎。

实际 8 条规则（`references/curated/action-rules.json`，依据锚点均可在 SPDX 全文逐字定位）：

| 顺序 | rule_id | level | when | 依据锚点 |
| --- | --- | --- | --- | --- |
| 1 | `A-REPL-001` | replace_or_license | 轴含 `same-license` + 与 outbound 不相容 | GPL-2.0-only §6 |
| 2 | `A-REPL-002` | replace_or_license | 依赖间不兼容 + 链接方式 `none`/`static` | Apache-2.0 §3 |
| 3 | `A-DECL-001` | declare | 轴恰为 `{notice}` + 相容 + 无依赖间冲突 | MIT 条件段 |

**五锚点门 + 确定性门（K20 / K7）**

- `package`（缺失 → `package_missing`）、`version`（缺失或 `*` → 按 `*` 记账 + `version_unknown`）、
  `declaration_location`（由 inventory 的 `evidence.file` + `locator`/`line` 组成字符串，
  给不出 → `declaration_location_missing`）、`spdx_id`、`basis_clause`
  （`规则条目 id｜anchor.ref section`，给不出 → `basis_clause_missing`）。
- 场景结论待确认（`scenario_pending_confirmation` / `scenario_record_missing`）、
  兼容性待定（`conflict_pending` / `conflict_record_missing`）、依赖间冲突未定（`pair_conflict_pending`）、
  义务轴映射不可用（`action_rules_unavailable`）→ 一律待确认，**不落 `ok`**。
- 缺项名写进 `evidence.missing_anchors`（与 §5.2 同名），原因码写进 `evidence.reason_codes`。
- **义务轴映射不可用即整张表不可用**：否则「轴为空」会被读成「没有义务」而误判 `ok`（K4 的硬边界）。

**退出码（§5.5 落地）**：`action.has_blocking_action` = 存在 `isolate` / `replace_or_license`
（`contract.BLOCKING_ACTION_LEVELS`）**或**存在任何待确认项。全量模式的退出码是四份产物的聚合
（profile / scenario / conflicts / actions）；`report` 的退出码 = 报告里有阻断级 **或** 待确认项非空。

**报告层（K19 / K23）**

- `report/sections.build_report(artifacts)` 是唯一章节结构来源：八个章节按 `contract.REPORT_SECTIONS`
  顺序产出，且**行**（`contract.REPORT_CSV_COLUMNS` 十列）就是「逐包明细」章节的数据。
- `report/markdown.py` 与 `report/csv_render.py` 都只消费它；CSV 走 `serialize.dumps_csv`
  （`lineterminator="\n"`、UTF-8 无 BOM——**P2 关闭：无 BOM**）。
- 免责声明逐字来自 `contract.DISCLAIMER`；「证据锚点」章节末尾固定引用中国司法参照
  （（2021）最高法知民终2063号，2023-05-05 终审），兑现 plan/00 的承诺台账。
- 三条 AST 守门由 `tests/test_report.py` 落地：① 不 import `licaudit.inventory` / `licaudit.assess`；
  ② 不出现 `BinOp`（`Add` 仅豁免「两侧都是字符串常量或 f-string」，因此报告层一律用
  `str.join` / `str.format`）；③ 不内联 SPDX ID、档位名、处置级别名字面量（展示标签从
  `contract.TIER_LABELS` / `contract.ACTION_LEVEL_LABELS` 取）。另加：渲染层不读盘、不读时钟。
- 报告只消费字段：未知字段忽略、不推导（测试用「插入未知字段后输出逐字节不变」锁定）。

**真值与基准**：`data/truth/actions.json`（`format = licaudit-actions-truth`）由
`tools/gen_action_truth.py` 从 curated 决策表 + curated 场景触发表**直接推导**，生成器不 import
生产处置引擎（谓词匹配用文件内独立朴素实现），`expect.levels` 保证四级各至少一个植入口。
`bench --only m5` 走 `verify.verify_actions`：192 组事实组合 + 4 条样本 = 196 条逐条对账，
另加「义务轴映射 / 可用条目集合与真值登记一致」的结构断言。

**示例项目与示例报告**：`data/synthetic/example-project/`（15 个依赖、六种清单形态、全合成包名）
+ `examples/report/`（两份运行：SaaS + `Elastic-2.0`、分发二进制 + `MIT`）。
**单场景下四级处置无法同时出现**：`declare` 需要「SaaS 场景 + 源可用档位 outbound」，
`replace_or_license` 需要「依赖间不兼容对」或「同许可义务 + 不相容 outbound」；
而 `declare` 要求的 outbound 档位是所有档位里最高的，档位级判定就不会再出现 `incompatible`。
两份运行合起来覆盖四级，且都由测试逐字节复现（见 plan/06 §五）。

**§4.6 传染范围聚合本轮仍未实现（D36）**：不新增 `linkage-boundary.json`；「边界是否可分离」
改由决策表的 `link_mode` 维度承担，聚合本身不做。已知偏差沿用 §4.7 的两类登记。

## 七、既定口径（K 清单的模块级落点）

后续里程碑「动了会打挂测试」的约定，统一登记在 `plan/05-里程碑.md` 与每份 HANDOFF。模块层先固定：
